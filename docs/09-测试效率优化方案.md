| 项目 | 内容 |
| --- | --- |
| 用途 | 把「验收测试」从模型逐屏看图确认，改成一次调用跑完、结果可判定的流水线 |

## 1. 一句话结论

**后期的「慢」不是执行慢，是决策粒度太细**：86 分钟的测试阶段里，90% 的时间在等模型对着一份 1.3M 字符的上下文、为「点一下按钮」这一个动作做一次完整往返。机器真正在跑的时间只有 **4.6%**。

所以优化方向不是换机器、加模拟器、并行编译，而是三件事：

1. **把 N 次往返压成 1 次**（场景脚本 / instrumented test）；
2. **把截图换成布局树文本**（~1.1 s / 6 KB vs 一轮 ~30 s）；
3. **把「自由巡场」换成「按 62 条 TC 逐条判定」**（有完成条件才会收敛）。

## 4. 目标架构：四层

```
┌─ L3  报告层 ────────────────────────────────────────────────┐
│  junit.xml + report.md：一次调用后只剩「读汇总」这一步        │
└──────────────────────────────────────────────────────────────┘
┌─ L2  场景层（本次已落地）────────────────────────────────────┐
│  tools/ui/run_scenario.py --filter TC-03                     │
│  一条命令 = 一个场景 = N 条断言；覆盖 instrumented 测不到的系统│
│  交互（SAF 文件选择器、系统弹窗、跨应用）                     │
└──────────────────────────────────────────────────────────────┘
┌─ L1  instrumented 层（待建）─────────────────────────────────┐
│  androidTest：Compose UI Test + in-memory Room               │
│  gradlew connectedDebugAndroidTest 一条命令跑完 62 条        │
└──────────────────────────────────────────────────────────────┘
┌─ L0  单测层（已有）──────────────────────────────────────────┐
│  TextRulesTest / PlanStatusTest / ExportCodecTest            │
│  纯 JVM，毫秒级，不占模型往返                                 │
└──────────────────────────────────────────────────────────────┘
```

**分工原则**：能在 L0 断言的规则绝不放到 L1；能在 L1 断言的界面绝不放到 L2；只有「系统 UI / 真实文件选择 / 跨进程」才落到 L2。

### 5.3 需要给生产代码开三个口子（约 20 行）

当前 `AppContainer` 在 `onCreate()` 里硬编码了 `Room.databaseBuilder(... "fieldnotes.db")`，测试无法注入内存库。改法：

```kotlin
// FieldNotesApp.kt —— 只动这三处
open class FieldNotesApp : Application() {
    lateinit var container: AppContainer
        private set

    override fun onCreate() {
        super.onCreate()
        container = createContainer()
    }

    /** 测试子类覆盖此方法以注入 in-memory 数据库。 */
    protected open fun createContainer(): AppContainer = AppContainer(this)
}

class AppContainer(context: Context, inMemory: Boolean = false) {
    // …
    internal val database: FieldNotesDatabase =
        if (inMemory) {
            Room.inMemoryDatabaseBuilder(appContext, FieldNotesDatabase::class.java)
                .allowMainThreadQueries()
                .build()
        } else {
            Room.databaseBuilder(appContext, FieldNotesDatabase::class.java, "fieldnotes.db").build()
        }
}
```

```kotlin
// androidTest —— 替换 Application
class TestFieldNotesApp : FieldNotesApp() {
    override fun createContainer(): AppContainer = AppContainer(this, inMemory = true)
}

class FieldNotesTestRunner : AndroidJUnitRunner() {
    override fun newApplication(cl: ClassLoader?, name: String?, context: Context?): Application =
        super.newApplication(cl, TestFieldNotesApp::class.java.name, context)
}
```

> 保留 `seedIfEmpty()`（6 个预置分类）不动——它正好是 [08](08-需求对照与验收清单.md) 里声明的验收前置条件。

### 5.4 关键前提：给 UI 加「可判定」的可观测点

现在的界面只有文本可断言。**「中划线 + 变灰」「红点」这类视觉规则，Compose 测试拿不到 `TextDecoration`，截图比对又脆又慢。** 正确做法是把它们暴露成语义状态——这同时满足 TC-046c 的读屏播报要求：

```kotlin
// 计划详情行：勾选态
Modifier.semantics {
    stateDescription = if (checked) "已收" else "未收"
}

// 计划卡片：红点态
Modifier.semantics {
    stateDescription = if (hasUnchecked) "有 $uncheckedCount 件物品未勾选" else "已全部打包"
}
```

于是测试变成纯文本断言，不需要任何像素：

```kotlin
composeRule.onNodeWithText("护照")
    .assert(SemanticsMatcher.expectValue(SemanticsProperties.StateDescription, "已收"))
composeRule.onNodeWithText("有 5 件物品未勾选", useUnmergedTree = true)
    .assertExists()
```

**约定**：所有需要断言的动态状态，一律通过 `stateDescription` / `contentDescription` / `testTag` 暴露，不靠视觉。这条约定写进 [05 · 功能设计文档](05-功能设计文档.md) 的界面规格里。

### 6.5 相比旧做法的四个硬修复

| 旧问题 | 现状 |
| --- | --- |
| `android layout` 裸调，无超时，挂死 2 分钟 | `subprocess` 硬超时 15 s + `--flat` 重试 + 超时连子进程树 `taskkill /T` |
| 冷启动后固定 `sleep`，抓到 systemui 的 4 个节点 | 轮询锚点文本，最多 15 s |
| 76 次坐标硬编码，误中相邻行 | 语义定位 + 节点自身 `center`，坐标不落盘 |
| 手动 `adb devices` / 猜 CLI 路径 | SDK 探测强制校验 `cmdline-tools/latest/bin/android.exe` |

### 6.6 两个实测坑（已写进代码注释）

1. **`uiautomator dump` 不可用**：本机 API 36 模拟器上返回 `exit 137`（SIGKILL）。所以降级链是 `layout -o` → `layout --flat` → 截图，**不要用 uiautomator 兜底**。
2. **PowerShell 5.1 下无 BOM 的 UTF-8 脚本会被按 GBK 解析**，中文直接破坏语法。本项目脚本统一用 Python（3.x 默认 UTF-8），避开整类问题。

## 7. P2 · 环境与超时治理

### 7.1 不要重装已经存在的工具

会话 02:28:15–02:31:45 花了 **3.5 分钟** 下载安装 `android` CLI 到 `%APPDATA%\AndroidCLI\android.exe`。实际上：

```
D:\Android\Sdk\cmdline-tools\latest\bin\android.exe   创建时间 2026-10-25 10:02
```

**它比会话早 16 小时就存在**，而 `android-ui-check` skill 正文里写的就是这个路径。根因：只查了 `$PATH` 就判定「没装」。

**规则**：环境探测按候选路径表逐个 `Test-Path`，绝不 `curl` 现场安装；探测失败先读 skill / 文档，再考虑安装。

### 7.2 超时策略

| 命令 | 前台超时 | 超时动作 |
| --- | --- | --- |
| `android layout` | 15 s | 换 `--flat` 重试一次，再失败则截图兜底 |
| `adb shell input / screenshot` | 20 s | 记录并跳过，不重试 |
| `gradlew assembleDebug` | 180 s | 保留为后台 job，用 `wait=false` 轮询 |
| `connectedDebugAndroidTest` | 600 s | 后台 job，结束后读 XML |

**后台 job 一律不要 `wait=true` 死等**：先用 `wait=false` 拉一次，去做别的，回头再收。旧会话 03:31:51 用 `wait=true timeout_ms=60000` 空等 60 s，就是反例。

### 7.3 首次装机只做一次

旧会话 3 轮重编译重装，每轮之后都要从首页重新点 3–6 下才能回到出问题的屏。建议：

- 调试期用 `adb install -r` 增量安装，不要 `assembleDebug` + 重装全流程；
- 需要回到特定页面时，注册 debug-only 深链（如 `fieldnotes://plan/3`）或注入状态快照，避免重走导航。

## 8. P3 · 会话与模型策略

| 策略 | 理由（实测） |
| --- | --- |
| **拆会话**：设计 / 编码 / 验收分开 | 验收一开始就背着 1.31M 字符，这是每一步 30 s 的地板价 |
| **验收会话只带** `08-验收清单` + 工程目录 | 不带 33 张原型图与 8 份设计文档 |
| **中途不切模型** | 4 次切换 = 4 次缓存全失效；T5 换模型后 58.0 s/步、最坏 270.9 s |
| **测试阶段一开始就加载 `android-ui-check`** | 旧会话直到用户 04:07 点名才加载，那时测试已跑完 |
| **显式声明完成条件** | 「62 条 TC 全绿」是可判定的；「把界面点一遍」不是，所以永远收敛不了 |
